## 1. OSI参照モデル / TCP/IPモデル

通信の仕組みを役割ごとに階層で分けた考え方です。「今の話がどの階層のことか」を意識すると、障害切り分けやツールの違いが理解しやすくなります。

| OSI参照モデル（7階層） | 役割 | 代表例 |
|---|---|---|
| 7. アプリケーション層 | アプリ間のやり取り | HTTP, DNS, SMTP |
| 6. プレゼンテーション層 | データ形式の変換・暗号化 | SSL/TLS, 文字コード |
| 5. セッション層 | 通信の開始〜終了の管理 | セッション確立 |
| 4. トランスポート層 | データの分割・信頼性確保 | TCP, UDP |
| 3. ネットワーク層 | 経路選択（ルーティング） | IP, ルーター |
| 2. データリンク層 | 直接つながった機器同士の通信 | Ethernet, MACアドレス, スイッチ |
| 1. 物理層 | 電気信号・光信号としての伝送 | LANケーブル, 光ファイバー |

実務では7階層すべてを意識することは少なく、より単純化した「TCP/IPモデル」（4階層）で語られることが多いです。

| TCP/IPモデル | OSI参照モデルとの対応 |
|---|---|
| アプリケーション層 | 7〜5層をまとめたもの |
| トランスポート層 | 4層 |
| インターネット層 | 3層 |
| ネットワークインターフェース層 | 2〜1層をまとめたもの |

「Webページが表示されるまで」で登場したDNS・HTTPはアプリケーション層、[web_basic.md](./web_basic.md#11-ネットワーク基礎) のIPアドレスはインターネット層、ポート番号はトランスポート層の話にあたります。

## 2. TCPとUDPの違い

どちらもトランスポート層のプロトコルですが、信頼性と速度のどちらを優先するかが異なります。

| | TCP | UDP |
|---|---|---|
| 接続 | 事前に接続を確立する（3ウェイハンドシェイク） | 接続確立をしない |
| 信頼性 | データの到達・順序を保証する（再送あり） | 保証しない（届かなくても再送しない） |
| 速度 | UDPより遅い | 速い |
| 代表用途 | HTTP, HTTPS, メール, ファイル転送 | 動画・音声通話, オンラインゲーム, DNSの一部 |

HTTPがTCP上で動くのは、Webページのデータが1バイトでも欠けたり順番が入れ替わったりすると困るためです。一方、動画通話では多少データが欠けても「速く届く」ことの方が重要なので、UDPが使われます。

### 3ウェイハンドシェイク

TCPが接続を確立するときの3段階のやり取りです。

```
クライアント →  SYN     → サーバー   (接続してよいか？)
クライアント ←  SYN/ACK ← サーバー   (よい。こちらも接続したい)
クライアント →  ACK     → サーバー   (了解、接続確立)
```

## 3. ルーター・スイッチ・ハブ

LANの中でよく見る機器で、それぞれ扱うデータの単位（＝OSI参照モデルの階層）が異なります。

| 機器 | 階層 | 役割 |
|---|---|---|
| ハブ | 物理層 | 届いたデータを接続されている全ポートに送り返す（単純な中継） |
| スイッチ | データリンク層 | MACアドレスを見て、宛先の機器がつながるポートにだけデータを送る |
| ルーター | ネットワーク層 | IPアドレスを見て、異なるネットワーク間の経路を選択する（LANとインターネットをつなぐ） |

家庭用の「Wi-Fiルーター」は、実際にはルーター・スイッチ・無線アクセスポイントの機能を1台にまとめた機器です。

## 4. NAT

NAT（Network Address Translation）は、**1つのグローバルIPを複数の端末で共有する**ための仕組みです。[web_basic.md](./web_basic.md#プライベートip--グローバルip) で説明したプライベートIP/グローバルIPの変換を担います。

```
PC(192.168.0.10)  ─┐
スマホ(192.168.0.11)─┼─ ルーター(NAT) ─ グローバルIP(1つ) ─ インターネット
プリンタ(192.168.0.12)┘
```

ルーターが「どの内部端末からのリクエストか」をポート番号などで管理し、外部からの応答を正しい端末に振り分けます。これにより、家庭内の複数端末がグローバルIPを1つしか持たなくてもインターネットに接続できます。

## 5. DHCP

DHCP（Dynamic Host Configuration Protocol）は、LANに接続した端末に**自動でIPアドレスを割り当てる**仕組みです。

| DHCPがない場合 | DHCPがある場合 |
|---|---|
| 端末ごとに手動でIPアドレスを設定する必要がある | ルーター（DHCPサーバー）が空いているIPアドレスを自動で貸し出す |

自宅や職場のWi-Fiに繋いだだけで通信できるようになるのは、ルーターがDHCPサーバーとして動作し、端末に自動でプライベートIPを割り当てているためです。

## 6. ファイアウォール

外部からの不正な通信を遮断する仕組みです。あらかじめ決めたルールに沿って、通信を通す/拒否するかを判断します。

| ルール例 | 動作 |
|---|---|
| ポート80, 443を許可 | Web閲覧はできる |
| ポート22を特定IPのみ許可 | SSHは社内ネットワークからのみ許可 |
| それ以外は拒否 | 上記以外の通信はすべて遮断 |

クラウド環境（AWSのセキュリティグループなど）でも、この「どのポート・どのIPからの通信を許可するか」という考え方は同じです。

## 7. リバースプロキシ

クライアントからのリクエストを一旦受け取り、裏側にある本来のサーバーに転送する仕組みです。クライアントからは、リバースプロキシがサーバーそのものに見えます。

```
クライアント → リバースプロキシ(Nginxなど) → アプリケーションサーバー(Flaskなど)
```

| 目的 | 内容 |
|---|---|
| 静的ファイル配信の高速化 | 画像・CSSなどはリバースプロキシが直接返し、アプリサーバーの負荷を減らす |
| HTTPS化（SSL終端） | 暗号化・復号をリバースプロキシ側でまとめて行う |
| 複数サーバーへの振り分け | 後述のロードバランサーとしても使われる |
| バックエンドの隠蔽 | 実際のアプリサーバーのIPやポートを外部から隠せる |

Flaskの開発サーバー（`flask run`）はそのまま本番公開せず、Nginxなどのリバースプロキシ経由で公開するのが一般的です。

---

## 8. ロードバランサー

1つのサービスに対して複数台のサーバーを用意し、リクエストを振り分ける仕組みです。リバースプロキシの一種として実装されることが多いです。

```
                 ┌→ サーバーA
クライアント → LB ┼→ サーバーB
                 └→ サーバーC
```

| メリット | 内容 |
|---|---|
| 負荷分散 | 1台に負荷が集中せず、複数台で処理を分担できる |
| 可用性向上 | 1台が落ちても他のサーバーで処理を続けられる |
| スケールしやすい | アクセス増加に合わせてサーバー台数を増やせる |

---

## 9. VPN

VPN（Virtual Private Network）は、インターネットのような公共の回線上に、暗号化された専用回線のような通信路を作る仕組みです。

| 用途 | 内容 |
|---|---|
| リモートワーク | 社外から社内ネットワークに安全に接続する |
| 通信の秘匿 | 公共Wi-Fiなどでの通信内容を暗号化して保護する |
| 地理的制限の回避 | 別の国・拠点を経由しているように見せる |

```
自宅PC → (暗号化トンネル) → VPNサーバー → 社内ネットワーク
```

VPNを使うと、自宅からでもプライベートIPの社内ネットワークに参加しているかのように通信できます。
